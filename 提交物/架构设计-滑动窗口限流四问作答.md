# 滑动窗口限流 · 四问作答

## 1. 用什么数据结构，核心逻辑怎么写

### 1.1 精确滑动窗口：每用户一个时间戳队列

结构是 `Map<userId, Deque<Long>>`，队列里存每次请求的**时间戳**，不存计数。存计数只能表达"这个固定窗口里有多少次"，表达不了"任意连续 N 秒内"；存时间戳，窗口才能连续右移。

```java
public final class SlidingWindowLimiter {
    private final long windowMillis;   // 窗口时长
    private final int  limit;          // 窗口内最大放行次数
    private final long idleMillis;     // 空闲多久回收该用户

    private final ConcurrentHashMap<String, Bucket> buckets = new ConcurrentHashMap<>();

    public boolean allow(String userId) {
        long now = System.currentTimeMillis();
        Bucket b = buckets.computeIfAbsent(userId, k -> new Bucket());
        synchronized (b) {                       // 锁粒度是单个用户，不是全局
            b.lastAccess = now;
            // ① 裁剪：丢弃滑出左边界的时间戳
            while (!b.events.isEmpty() && now - b.events.peekFirst() >= windowMillis) {
                b.events.pollFirst();
            }
            // ② 判定：窗口内还有余量才放行
            if (b.events.size() < limit) {
                b.events.addLast(now);
                return true;
            }
            return false;
        }
    }

    /** 清理不活跃用户：低频定时任务调用 */
    public void evictIdle() {
        long threshold = System.currentTimeMillis() - idleMillis;
        buckets.entrySet().removeIf(e -> e.getValue().lastAccess < threshold);
    }

    private static final class Bucket {
        final Deque<Long> events = new ArrayDeque<>();   // 已在锁内访问，无需并发容器
        long lastAccess;
    }
}
```

**不变式**：裁剪 → 计数 → 入队，三步必须在同一临界区内。拆开就会出现两个线程同时看到 `size < limit`、双双入队、实际放行 `limit + 1` 次。单机靠 `synchronized(b)`，集群靠 Redis Lua（见第 4 问）。

时间戳有序，所以裁剪是队头出队，不需要遍历查找；新请求队尾入队。

### 1.2 近似滑动窗口：分桶计数（limit 很大时的省内存变体）

把窗口切成 `N` 个槽，每槽一个计数，窗口和 = 各槽计数之和，窗口前进一格清一格。

```java
long slot = now / slotMillis;
if (slot != lastSlot) {
    for (long s = lastSlot + 1; s <= slot; s++) slots[(int)(s % N)] = 0;   // 跳几格清几格
    lastSlot = slot;
}
long sum = Arrays.stream(slots).sum();      // 维护 runningSum 可做到 O(1)
if (sum < limit) { slots[(int)(slot % N)]++; return true; }
return false;
```

空间从"窗口内请求数"降到固定的 `N` 个槽，与 `limit` 无关；代价是精度退化，误差上限约 `limit × 2/N`。要求严格"任意连续窗口不超过 limit"就用 1.1，限流粒度粗、QPS 极高、内存敏感时用这版。

## 2. 时间、空间复杂度

| 方案 | 单次 `allow` 时间 | 空间 | 说明 |
|---|---|---|---|
| 精确滑动窗口（时间戳队列） | 摊还 **O(1)**，最坏 **O(k)** | **O(U × W)** | k = 本次裁剪的过期戳个数；U = 活跃用户数；W = 单用户窗口内实际请求数（≤ limit） |
| 近似滑动窗口（分桶计数） | 严格 **O(1)** | **O(U × N)** | N = 槽数，与 limit 无关 |
| Redis ZSET 版 | **O(log W + M)** + 1 次 RTT | O(U × W) | M = 本次移除的成员数 |
| Redis Hash 令牌桶版 | **O(1)** + 1 次 RTT | **O(U)** | 只存 2 个字段 |

**精确版为什么是摊还 O(1)**：每个时间戳一生只入队一次、出队一次，n 次请求的总出队次数 ≤ n，摊下来 O(1)。某一次请求可能一次性淘汰 k 个过期戳（用户静默很久后再来），但 k ≤ limit，最坏有界。

**空间是否有界**：是。窗口裁剪 + 不活跃用户回收（集群版靠 key TTL），稳态内存 ≈ 活跃用户数 × 窗口内请求数。

## 3. 固定窗口 / 滑动窗口 / 令牌桶 / 漏桶 各自适合什么场景

| 算法 | 机制 | 任意连续窗口精确 | 突发 | 单位存储 | 场景 |
|---|---|---|---|---|---|
| 固定窗口 | 按整点时间桶计数，到点清零 | ❌ 边界可放 2×limit | 允许 | 1 个计数 | 粗粒度配额、统计计费、对临界突刺不敏感 |
| 滑动窗口 | 维护窗口内时间戳，窗口连续右移 | ✅ 精确 | 窗口内有余量即可 | 时间戳列表 | 按用户防刷、精确 QPS / 配额限制、开放 API 配额 |
| 令牌桶 | 恒定速率产令牌，请求取令牌 | 近似（限速率） | ✅ 桶满可一次取空 | 令牌数 + 时间戳 | 限速但允许短时突发：登录、短信验证码、推送 |
| 漏桶 | 请求入桶，恒定速率出桶，溢出丢弃 | 近似（限速率） | ❌ 强制平滑 | 水位 + 时间戳 | 保护脆弱下游、削峰填谷：付费第三方 API、数据库写入、网关出向 |

**固定窗口的临界突刺**：窗口 1 分钟、limit=100，用户在 00:59 打满 100 次，01:00 清零后又打满 100 次 → 这 2 秒内实际放行 200 次，是 limit 的 2 倍。滑动窗口始终按"过去 60 秒"计算，第二次会被前 100 次挡住。

**令牌桶 vs 漏桶**：令牌桶限制平均速率，允许"攒着不用、一次性爆发"；漏桶限制瞬时输出速率，进来多猛出去都匀速，多余的直接丢弃。两者都是速率整形，语义上**不等于**"任意连续 N 秒不超过 limit"。

**选型**：要精确计数 → 滑动窗口；要省内存 + 粗粒度 → 固定窗口；要限速但允许突发 → 令牌桶；要绝对匀速保护下游 → 漏桶。

## 4. Redis 做集群限流：key、数据结构、原子操作

### 4.1 为什么要下沉到 Redis

单机 `ConcurrentHashMap` 在多副本部署下失效：每台机器各计各的，全局实际放行 = `limit × 机器数`。要全局配额就必须有共享状态存储。

### 4.2 Key 设计

```
ratelimit:{userId}          # 按用户
ratelimit:{api}:{userId}    # 按接口 + 用户
```

**hash tag 规则**：Redis Cluster 只对 key 中第一对 `{}` 内的子串做 CRC16 分槽。`ratelimit:{alice}` 与 `ratelimit:{alice}:seq` 参与分槽的都是 `alice`，同槽；写成 `ratelimit:alice:seq`（不带花括号）则极可能落在不同 slot，Lua 会报 `CROSSSLOT`。**同一次原子操作涉及的所有 key 必须共享同一个 hash tag。**

### 4.3 三种结构对比

| 方案 | 结构 | 精度 | 内存 | 单次开销 | 适用 |
|---|---|---|---|---|---|
| A 固定窗口 | String + `INCR`/`EXPIRE` | ❌ 边界 2×limit | O(1)/用户 | O(1) | 粗粒度、海量用户 |
| B 精确滑动窗口 | ZSET（score=时间戳，member=唯一串） | ✅ 精确 | O(窗口内请求数) | O(log W + M) | 严格要求任意连续窗口 |
| C 令牌桶 | Hash（tokens + lastTs） | 近似（速率） | O(1)/用户 | O(1) | 限速 + 允许突发 |

### 4.4 方案 B：ZSET + Lua

```lua
-- KEYS[1] = ratelimit:{userId}
-- ARGV[1] = now(ms)  ARGV[2] = windowMs  ARGV[3] = limit
-- ARGV[4] = ttlMs    ARGV[5] = 唯一后缀（客户端生成，如 uuid）
local key    = KEYS[1]
local now    = tonumber(ARGV[1])
local window = tonumber(ARGV[2])
local limit  = tonumber(ARGV[3])
local ttl    = tonumber(ARGV[4])
local uniq   = ARGV[5]

-- ① 裁剪：丢弃滑出窗口的成员
redis.call('ZREMRANGEBYSCORE', key, 0, now - window)

-- ② 计数
local cnt = redis.call('ZCARD', key)

-- ③ 判定 + 写入，与 ①② 同属一个脚本，天然原子
if cnt < limit then
  redis.call('ZADD', key, now, now .. ':' .. uniq)
  redis.call('PEXPIRE', key, ttl)
  return 1
end

-- 被拒绝时也续 TTL，避免"只被拒绝、不再请求"的 key 提前消失导致计数失真
redis.call('PEXPIRE', key, ttl)
return 0
```

三个坑：

1. **member 必须唯一**。同毫秒的多个请求若都用 `now` 当 member，`ZADD` 会被当成更新同一成员，计数少算、限流失效，所以要拼 `now:uuid`。
   反例：`now .. ':' .. redis.call('INCR', key .. ':seq')` 会凭空多出 `ratelimit:{userId}:seq` 这个 key，而它**没有 TTL**，用户不活跃后永久残留，等于制造内存泄漏。不用自增 key，要用就给它同样设 `PEXPIRE`。
2. **`now` 由应用服务器传入，不在脚本里取 `TIME`**。保证脚本是确定性函数，主从复制与持久化回放结果一致（Redis 5 起默认 effects replication 才允许脚本内 `TIME`，老版本直接报错）。多机时钟漂移用 NTP 兜底。
3. **TTL 要大于窗口**，取 `window × 2`。若 TTL = window，key 可能在窗口滑完前就过期，用户反而多出配额。

### 4.5 原子性：为什么用 Lua 而不是 MULTI/EXEC

- 需要的是"读 → 判断 → 写"，写什么取决于读到什么。Redis 事务只是把命令排队后一次性执行，**事务内读不到中间结果**，无法分支。
- `WATCH` + `MULTI` 能做乐观锁，但失败要重试，高并发下重试风暴。
- Lua 脚本在 Redis 单线程原子执行，期间不会有其他命令插入，等价于单机版那把 `synchronized(b)`，且只需 1 次网络往返。
- 工程细节：用 `EVALSHA` 避免每次传整段脚本，首次 `NOSCRIPT` 回退 `EVAL`；脚本内不要写死循环或耗时操作，会阻塞 Redis 单线程。

### 4.6 集群与运维

- **同槽**：key 统一带 hash tag，Lua 涉及的 key 必须同 slot。
- **热 key**：极端热点用户会把流量压到单 slot，可拆成 N 个子桶（`ratelimit:{userId}:{0..N-1}`，tag 仍是 userId 保证同槽），配额按子桶分摊。
- **降级**：Redis 不可用时不要硬拒绝全部请求，常见做法是"放行 + 打点告警"，或切本地令牌桶用保守阈值兜底，避免限流组件拖垮主流程。
- **可观测**：`ZCARD` 即当前窗口用量；拒绝率、脚本 P99 耗时、key 数量打点；`SLOWLOG` 盯 Lua 执行时间。
